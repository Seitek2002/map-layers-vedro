# Картографические слои — тестовое задание

React + TypeScript + [vedro](https://www.npmjs.com/package/vedro) (легковесный
селектор-based стор). Три слоя из задания (температура/ветер/инсоляция) заданы
конфигом, а не захардкожены как отдельные компоненты — архитектура рассчитана
на 100+ слоёв без изменений в коде.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # прод-сборка + tsc -b
npm test         # vitest (race-condition тесты)
npm run lint     # oxlint — 0 warnings
```

## Карта

Помимо панели управления есть настоящая карта (`react-leaflet` + тайлы
OpenStreetMap, без ключей API). Каждый слой рисуется как цветной прямоугольник
поверх карты — это делает связь «состояние в vedro → что видно на карте»
буквальной, а не декоративной:

- прямоугольник показывается только когда `layer.enabled && layer.status ===
  "success"` — включение слоя, ошибка загрузки и успех реально влияют на то,
  что нарисовано;
- `fillOpacity` прямоугольника напрямую берётся из `layer.opacity` — двигая
  слайдер, буквально видно, как слой становится прозрачнее;
- координаты и цвет — чистая функция от `id` слоя (`src/map/layerGeometry.ts`,
  детерминированный хэш строки → ячейка сетки 12×12, с зазором между ячейками,
  чтобы соседние слои не наезжали друг на друга). Геоданные нигде не хранятся
  в сторе — это чисто презентационная деталь, а не часть состояния;
- `MapLayerOverlay` — точная копия архитектуры `LayerRow`: свой селектор на
  `layers[id]`, `React.memo`, поэтому переключение одного слоя не трогает
  прямоугольники остальных на карте.

## Структура состояния

```ts
LayersState = {
  layerIds: LayerId[];                 // порядок слоёв
  layers: Record<LayerId, LayerState>; // нормализованные данные слоя
}
```

Нормализация (ids + entities, как в Redux `createEntityAdapter`) — ключевое
решение для масштабируемости: добавление слоя трогает только `layerIds` и
`layers`, а не создаёт новых полей стора вида `temperatureEnabled`,
`windOpacity` и т.д. `LayerList` подписан только на `layerIds`, `LayerRow` —
только на свой `layers[id]`. Подробности ниже, в разделе про рендеры.

## Управление состоянием в vedro

`createVedro<LayersState>(initialState)` (`src/store/layersStore.ts`) даёт
`Provider`, `useStore`, `useSelector`. Вся мутация состояния идёт через
`store.dispatch(...)`, никогда напрямую.

Вся бизнес-логика действий вынесена в чистую фабрику
`createLayerActions(store, controllers)` (`src/store/layerActions.ts`), не
зависящую от React — это позволяет тестировать race conditions в vitest без
монтирования компонентов (`src/store/layerActions.test.ts`), и даёт хукам
(`useLayerActions`) быть тонкой обвязкой.

### Важная находка: в vedro@1.1.0 асинхронный `dispatch` не работает

В README библиотеки документирован `dispatch(async (state) => {...})`. Но в
`node_modules/vedro/lib/helpers/typeCheck.js`:

```js
var isAsyncFunction = function (fun) { return fun instanceof Promise; };
```

Это проверяет, является ли *ссылка на функцию* экземпляром `Promise` — что
всегда `false` (промисом является результат её вызова, а не сама функция).
Из-за этого `Vedro.dispatch()` (`_Vedro.js`) для async-колбэка всегда уходит
в синхронную ветку `dispatchWithCB`, где `cb(state)` возвращает необращённый
`Promise`, у которого при спреде `{...state, ...promise}` нет собственных
enumerable-полей — стейт молча остаётся прежним, ответ запроса теряется.

Проверено напрямую: `npm view` / чтение исходников пакета в
`node_modules/vedro`, а не только README.

**Следствие для архитектуры:** асинхронная оркестрация (загрузка слоя) сделана
*снаружи* vedro, а не через его async-dispatch. Каждый шаг запроса —
loading → success|error — коммитится отдельным **синхронным** `dispatch`
(`patchLayer` в `layerActions.ts`), который используют оба рабочих
перегруженных сигнатуры (`(state) => Partial<S>` и `Partial<S>`). Это чище и
предсказуемее, чем чинить/патчить сторонний пакет.

## Race conditions при быстрых переключениях

`createLayerActions` хранит `Map<LayerId, AbortController>` (вне реактивного
состояния — это императивный, не отображаемый в UI ресурс, ему не место в
сторе). При каждом `setEnabled(id, true)`/`retry(id)`:

1. Предыдущий `AbortController` для этого `id` отменяется (`.abort()`).
2. Создаётся новый, тут же кладётся в `Map`.
3. `fetchLayerData` вызывается с его `signal`; и `.then`, и `.catch`
   первым делом проверяют `controller.signal.aborted` — если да, результат
   отменённого запроса просто отбрасывается.

Таким образом на любую последовательность вкл/выкл/вкл всегда применяется
только исход **последнего** запроса, независимо от порядка резолва промисов.
Поле `requestVersion` в `LayerState` — не механизм защиты (её обеспечивает
`AbortController`), а диагностика: тест
`"only applies the outcome of the latest request when toggled rapidly"`
явно резолвит три перекрывающихся запроса в неправильном порядке и проверяет,
что счётчик и статус соответствуют именно последнему.

Живая проверка в браузере (production-сборка, без StrictMode): 5 быстрых
кликов по чекбоксу «Ветер» → ровно 7 рендеров (1 монтирование + 5 переключений
+ 1 финальный success), финальный статус — консистентный «Готово», без
зависаний в loading и без «воскресших» устаревших ошибок.

## Отсутствие лишних render

Три независимых механизма, проверены наблюдаемо (счётчик `renders: N` в
каждой строке — намеренная отладочная проба, см. `LayerRow.tsx`):

1. **Гранулярные селекторы.** `LayerRow` подписан на `state.layers[id]`, а не
   на весь `layers`. vedro сравнивает результат селектора через
   `JSON.stringify` при каждом dispatch — если чужой слой поменялся, сериализация
   *своего* среза не меняется → `setState` не вызывается → row не
   перерисовывается. `LayerList` подписан только на `layerIds`, поэтому смена
   статуса/прозрачности любого слоя его не трогает.
2. **`React.memo`.** Когда `layerIds` меняется (добавили слои), `LayerList`
   перерисовывается и пересоздаёт JSX для *всех* строк, включая старые — но
   `React.memo(LayerRowImpl)` останавливает лишний рендер там, где `id`
   не изменился по значению.
3. **Debounce коммита прозрачности.** `OpacitySlider` держит локальный
   `draft` (мгновенная визуальная обратная связь на каждый пиксель) и
   коммитит в vedro не чаще раза в 80 мс — иначе каждый tick драга слайдера
   фан-аутил бы `dispatch` на вообще все смонтированные селекторы в
   приложении (см. следующий раздел про масштабирование).

Замер (production-сборка): после добавления 100 слоёв кнопкой
«Добавить слои» счётчики `renders` у трёх исходных строк **не изменились** —
рост списка не трогает уже смонтированные строки.

## Масштабирование с 5 до 100+ слоёв

- Нормализованный стор + конфиг слоёв (`layerDefinitions.ts`) — добавление
  слоя это один элемент массива, а не новый код/компонент/поле стора.
- Кнопка «Добавить слои (тест масштабирования)» в тулбаре реально добавляет
  N слоёв в рантайме — можно своими глазами увидеть 100+ строк без правки
  кода.
- **Известный потолок самого vedro**, о котором стоит сказать честно: у него
  ровно один канал подписки — `store.on("@state", cb)`; `notifyStateSubs`
  (`_Notifier.js`) на **каждый** dispatch обходит *все* смонтированные
  `useSelector`, а не только те, чей срез реально изменился (сама фильтрация
  происходит уже внутри каждого коллбэка через `JSON.stringify`-сравнение).
  То есть стоимость одного dispatch — `O(число подписок)`, а не `O(что
  реально изменилось)`. На сотнях слоёв (сотни-тысячи подписок) это
  недорого (мелкие объекты, синхронная работа в пределах одного тика). На
  10 000+ слоёв или очень частых обновлениях (потоковые данные) этот канал
  стал бы узким местом, и потребовалась бы либо доработка стора под
  key-based подписки (`store.on(key, cb)` у vedro уже есть, но `useSelector`
  им не пользуется), либо переход на стор с честной топиковой подпиской.
  Для заявленного диапазона (5–100+) это не проблема, но масштаб, на
  котором подход перестаёт быть бесплатным, стоит знать заранее.

## Строгая типизация

`tsconfig.app.json`: `strict`, `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`, `noImplicitReturns`. `any` нигде не
используется (проверяется `oxlint` — 0 warnings/errors). Доступ к
`layers[id]` типизируется как `LayerState | undefined` из-за
`noUncheckedIndexedAccess`; компоненты обрабатывают это явной проверкой
(`if (!layer) return null`), без `!`-ассершенов.

## Тесты

Два уровня:

- `src/store/layerActions.test.ts` — юнит-тесты чистой логики действий поверх
  голого экземпляра `Vedro` (без монтирования React): успешная загрузка,
  **race condition** (три пересекающихся запроса резолвятся не по порядку —
  итог соответствует только последнему), ошибка → `retry` → восстановление,
  bulk-добавление 100 слоёв.
- `src/components/LayerList.test.tsx` — интеграционные тесты через
  `@testing-library/react` поверх настоящего `LayersStoreProvider`: чекбокс →
  DOM доходит до «Готово», ошибка показывает кнопку retry и восстанавливается,
  соседняя строка не перерисовывается при изменении другого слоя (тот же
  факт, что проверялся вручную в браузере, здесь — как регрессионный тест).

```

  types/layer.ts            — доменные типы
  api/mockLayerApi.ts        — имитация запроса (задержка + случайная ошибка + abort)
  store/
    layerDefinitions.ts       — конфиг трёх слоёв из задания
    buildLayersState.ts       — фабрика начального состояния
    layersStore.ts            — createVedro + экспорт Provider/useSelector
    layerActions.ts            — чистая логика действий + race-condition guard
    layerActions.test.ts       — юнит-тесты
  hooks/
    useLayerActions.ts          — React-обвязка над createLayerActions
    useLayerActionsContext.ts   — доступ к actions без прокидывания пропсами
  context/                       — Provider + сам Context-объект (раздельно, ради Fast Refresh)
  components/
    LayerList.tsx                — подписан на layerIds
    LayerList.test.tsx            — интеграционные тесты (DOM + vedro)
    LayerRow.tsx                  — подписан на layers[id], React.memo
    OpacitySlider.tsx              — локальный draft + debounce-коммит
    StatusBadge.tsx                 — чистая презентационная часть
    Toolbar.tsx                      — агрегаты + demo-контролы масштабирования
  map/
    layerGeometry.ts               — id → координаты/цвет (чистая функция, детерминированный хэш)
    LayerMap.tsx                    — MapContainer, подписан на layerIds
    MapLayerOverlay.tsx             — прямоугольник слоя, подписан на layers[id], React.memo
  test/setup.ts                     — jest-dom матчеры + автo-cleanup для vitest
```
