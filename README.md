# Картографические слои — тестовое задание

React + TypeScript + [vedro](https://www.npmjs.com/package/vedro). Слои
(температура/ветер/инсоляция) заданы конфигом, а не захардкожены как
отдельные компоненты — рассчитано на 100+ слоёв без изменений в коде.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # прод-сборка + tsc -b
npm test         # vitest
npm run lint     # oxlint — 0 warnings
```

## Использование AI-инструментов

Решение реализовано в связке с **Claude Code** (Anthropic) — от архитектуры
до финальной проверки в браузере (`agent-browser`: реальные клики по
чекбоксам, слайдерам, чтение DOM/счётчиков рендеров, сверка dev/prod-сборки).

Ключевые моменты, где ИИ работал не как генератор кода, а как исследователь:

- по просьбе не доверять README библиотеки, а свериться с исходниками —
  ИИ прочитал `node_modules/vedro` и нашёл, что `dispatch(async cb)` там не
  работает (см. «Управление состоянием в vedro» ниже);
- баг наложения слоёв на карте (свой же код) был пойман не рассуждением, а
  скриншотом реального рендера, и это привело к смене подхода (`bounds`
  вместо ручного `center`/`zoom`);
- race condition проверен не только юнит-тестом, но и вживую — 5 быстрых
  кликов по чекбоксу и сверка финального состояния.

Что решал я сам: архитектурные развилки с trade-off'ами (например, добавлять
ли настоящую карту, хотя задание допускало минимальный UI) ИИ выносил на моё
решение явными вопросами, а не додумывал сам; имя/видимость репозитория;
финальный ревью кода и README перед публикацией.

## Архитектура состояния

```ts
LayersState = {
  layerIds: LayerId[];                 // порядок слоёв
  layers: Record<LayerId, LayerState>; // нормализованные данные
}
```

Нормализация (ids + entities) — добавление слоя трогает только `layerIds` и
`layers`, а не заводит новые поля стора вида `temperatureEnabled`. `LayerList`
подписан на `layerIds`, `LayerRow`/`MapLayerOverlay` — каждый на свой
`layers[id]`.

`createVedro<LayersState>(...)` (`layersStore.ts`) даёт `Provider`,
`useStore`, `useSelector`. Логика действий вынесена в чистую фабрику
`createLayerActions(store, controllers)` (`layerActions.ts`), не зависящую от
React — это даёт тестировать race conditions в vitest без монтирования
компонентов.

### Находка: в vedro@1.1.0 асинхронный dispatch не работает

```js
// node_modules/vedro/lib/helpers/typeCheck.js
var isAsyncFunction = function (fun) { return fun instanceof Promise; };
```

Проверяет ссылку на функцию на `instanceof Promise` — всегда `false`
(промис — результат вызова, не сама функция). Из-за этого async-колбэк в
`dispatch()` уходит в синхронную ветку, где спред необращённого `Promise` не
даёт enumerable-полей — стейт остаётся прежним, ответ запроса теряется.

**Следствие:** асинхронная оркестрация сделана *снаружи* vedro — каждый шаг
(loading → success|error) коммитится отдельным синхронным `dispatch`.

## Race conditions при быстрых переключениях

`createLayerActions` хранит `Map<LayerId, AbortController>` вне стора (это
императивный ресурс, не UI-состояние). На каждый `setEnabled`/`retry`:
предыдущий контроллер для этого `id` отменяется, создаётся новый; и
`.then`, и `.catch` первым делом проверяют `signal.aborted` и отбрасывают
устаревший результат. Итог: на любую последовательность вкл/выкл всегда
применяется исход только последнего запроса — проверено юнит-тестом (три
запроса резолвятся не по порядку) и вживую (5 быстрых кликов → консистентный
финальный статус, без зависаний и «воскресших» ошибок).

## Отсутствие лишних render

- **Гранулярные селекторы** — `LayerRow`/`MapLayerOverlay` подписаны на
  `layers[id]`, а не на весь `layers`; чужой слой меняется — сериализация
  своего среза не меняется — `setState` не вызывается.
- **`React.memo`** — рост `layerIds` пересоздаёт JSX всех строк, но memo
  останавливает рендер там, где `id` не изменился.
- **Debounce опасити** — `OpacitySlider` коммитит в vedro не чаще раза в
  80 мс, иначе каждый tick драга фан-аутил бы dispatch на все подписки.

Замерено вживую (prod-сборка): добавление 100 слоёв не меняет счётчики
рендеров у уже смонтированных строк.

## Масштабирование с 5 до 100+ слоёв

Нормализованный стор + конфиг слоёв — добавление слоя это один элемент
массива. Кнопка «Добавить слои» в тулбаре реально добавляет N слоёв в
рантайме.

Честно про потолок самого vedro: один канал подписки (`on("@state", cb)`) —
каждый dispatch обходит *все* смонтированные селекторы, фильтрация происходит
уже внутри через `JSON.stringify`-сравнение. Это `O(число подписок)` на
dispatch, а не `O(что реально изменилось)`. На сотнях слоёв — бесплатно, на
10 000+ или при очень частых обновлениях стал бы узким местом.

## Типизация и тесты

`strict` + `noUncheckedIndexedAccess` в tsconfig, `any` нигде не используется
(проверяется линтером). `layers[id]` типизирован как `LayerState | undefined`
— компоненты обрабатывают это явной проверкой, без `!`-ассершенов.

Два уровня тестов: юнит (`layerActions.test.ts` — race condition, retry,
bulk-add поверх голого `Vedro`, без React) и интеграционные
(`LayerList.test.tsx` — через `@testing-library/react` поверх настоящего
Provider, включая тест «соседняя строка не перерисовывается»).

## Карта

`react-leaflet` + тайлы OpenStreetMap (без ключей API). Каждый слой — цветной
прямоугольник, который виден только когда `layer.enabled && layer.status ===
"success"`, а его `fillOpacity` берётся из `layer.opacity` — связь «стор →
карта» буквальная. Координаты/цвет — чистая функция от `id`
(`map/layerGeometry.ts`), в сторе геоданные не хранятся.
